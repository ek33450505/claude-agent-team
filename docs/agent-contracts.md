# Agent Contract Testing

CAST agent contracts are machine-verifiable specifications that define what a well-behaved agent response must contain. Contracts run against fixture files (recorded agent outputs), not live API calls, so they are fast, deterministic, and safe to run in CI.

---

## Why Regex, Not Exact Match

Agent outputs are generated by LLMs. Even with identical prompts, the exact phrasing of a status block or work log section will vary across models, model versions, and context lengths. Exact-match assertions would produce flaky tests — passing today, failing after a model update, with no meaningful signal either way.

Regex patterns capture *structural intent*: "the output contains a Status line with one of these values" rather than "the output contains exactly this string." This makes contracts resilient to natural LLM variance while still catching real regressions (e.g., an agent that stopped emitting a Work Log, or a commit agent that started issuing raw `git commit` commands).

## Assertion Types

### `output_contains`

Asserts the agent's full text output matches a regex pattern. Uses Python `re.search`, so patterns match anywhere in the output.

```yaml
- type: output_contains
  pattern: "Status: (DONE|DONE_WITH_CONCERNS|BLOCKED|NEEDS_CONTEXT)"
```

Use this for: structural markers (Status block, Work Log header), required keywords, format checks.

### `output_not_contains`

Asserts the agent's output does NOT match the pattern. Useful for prohibitions.

```yaml
- type: output_not_contains
  pattern: "^git commit"
```

Use this for: anti-patterns (an agent that should use an abstraction not raw commands), sensitive data that must not appear in output.

### `cast_db_write`

Asserts that after running, a row exists in the specified `cast.db` table where `field = expected`. The contract runner queries `~/.claude/cast.db` after evaluating output assertions.

```yaml
- type: cast_db_write
  table: agent_runs
  field: agent_name
  expected: commit
```

Use this for: verifying observability — that the agent actually logged its run to cast.db. This catches agents that run but skip telemetry.

### `exit_code`

Asserts the agent runner process exited with a specific code.

```yaml
- type: exit_code
  expected: 0
```

Use this for: scripts that must exit cleanly, or failure scenarios where exit 1 is the expected outcome.

## Recording Fixtures

The `--record` flag runs the actual agent and saves its output as a fixture file:

```bash
cast test --record commit
```

This dispatches the commit agent with the fixture's `input` prompt, captures the full output, and writes it to `agent-contracts/fixtures/<agent>-<fixture-slug>.txt`.

Recorded fixtures should be reviewed before committing — they are the ground truth that future contract runs evaluate against. If a fixture is recorded from a broken run, it encodes the wrong behavior.

**Fixture naming convention:** `<agent-name>-<fixture-slug>.txt` where `fixture-slug` is the fixture `name` field lowercased with spaces replaced by hyphens.

## Adding a Contract for a New Agent

1. **Create the contract file** at `agent-contracts/<agent-name>.contract.yaml`. Use the format below.

2. **Add at least 3 assertions:**
   - One for the Status block (`output_contains` with the full Status pattern)
   - One for a structural marker specific to that agent
   - One `cast_db_write` assertion for telemetry

3. **Add at least 1 fixture** with a realistic `input` prompt and `expected_status`.

4. **Record a baseline fixture file:**
   ```bash
   cast test --record <agent-name>
   ```

5. **Verify the contract passes** against the recorded fixture:
   ```bash
   cast test <agent-name>
   ```

6. **Add to `agent-contracts/README.md`** with a one-line description.

## Complete Annotated Contract Example

```yaml
# agent-contracts/commit.contract.yaml

# The name of the agent this contract covers.
# Must match the agent's frontmatter `name:` field.
agent: commit

# Contract schema version. Increment when the assertion format changes.
# Not the agent's version — the contract format version.
version: "1.0"

assertions:
  # Every CAST agent must end with a Status block.
  # Regex covers all four valid status values.
  - type: output_contains
    pattern: "Status: (DONE|DONE_WITH_CONCERNS|BLOCKED|NEEDS_CONTEXT)"

  # Every agent that performs work must include a Work Log section.
  - type: output_contains
    pattern: "## Work Log"

  # The commit agent must write to cast.db agent_runs with agent_name = commit.
  # This verifies the observability pipeline is wired, not just that the output looks right.
  - type: cast_db_write
    table: agent_runs
    field: agent_name
    expected: commit

  # The commit agent must use the commit abstraction, not raw git commands.
  # This is a behavioral contract — a regression here indicates the agent
  # is bypassing the quality gate that commit hooks enforce.
  - type: output_not_contains
    pattern: "^git commit"

fixtures:
  # Each fixture is a named scenario. The `input` is the prompt given to the agent.
  # The fixture file lives at: agent-contracts/fixtures/commit-basic.txt
  - name: "basic commit"
    input: "Create a commit for changes to README.md"
    # Optional: mock files the agent will see. Used by --record mode.
    mock_files:
      - path: README.md
        content: "# Changed"
    # The expected top-level status value in the agent's response.
    expected_status: DONE
```

## Contract Runner

Run contracts with the `cast test` subcommand:

```bash
cast test                    # run all contracts
cast test commit             # run one agent's contract
cast test --record commit    # record a new fixture from a live run
cast test --ci               # no ANSI color, machine-readable exit codes
```

Results are written to `cast.db` table `contract_test_runs` and shown in `cast status`.

See also: `scripts/cast-contract-runner.sh`, `scripts/cast_contract_runner.py`.
